# solpay-ai 상세 기록

결제 화면 카드 배치 엔진과 AI 기능(챗봇·일정 분류·추천 문구)을 담은 FastAPI 서버의 실행·학습·평가·API·운영 방법이다.
카드 순서만 정하고 결제 확정은 고객이 한다. 앱은 백엔드(Spring)만 부르고, 백엔드가 이 서버의 `/internal/*` 를 부른다.

- 알고리즘 설명: `docs/설계/카드배치_알고리즘_설계서.md`
- 챗봇 설명: `docs/설계/LLM_챗봇_설계서.md`, 검증 `docs/설계/챗봇_500문항_검증_보고서.md`
- 휴대폰 시연용 가상 POS 는 저장소 `demo/` 에 있고, 저장소 루트 `run_phone_demo.sh` 가 이 서버·백엔드·가상 POS 를 함께 켠다.
- 가상 데이터의 혜택과 소비는 임의 값이다. 평가 수치는 알고리즘 동작 검증이지 실제 절감액이 아니다.

## 1. 폴더 구성

| 폴더 | 내용 | 배포 |
|---|---|---|
| `engine/` | 배치 엔진, AI 기능, API | 그대로 배포 |
| `engine/chat/` | 챗봇(도구 17개), 일정 직접 입력 분류, 추천 페이지·월간 리포트 문구 | 그대로 배포 |
| `training/` | 전체 사용자 분포, LightGBM 업종 모델, 기준값 비교 | 학습할 때만 |
| `evaluation/` | 재생 평가, 사후 최적 상한, 데모 보고서, 챗봇·문구·분류 평가 | 평가할 때만 |
| `scripts/` | 로컬 DB 준비, Postgres 적재, API 명세 내보내기 | 필요할 때 |
| `sql/` | `001_placement.sql`(엔진용 표), `002_app.sql`(쓰기용 app 스키마) | DB 에 적용 |
| `tests/` | 자동 시험 | CI |
| `postman/` | API 시나리오 시험 | 서버를 켜고 |
| `artifacts/` | 학습 결과·평가 보고서 (깃 제외) | `priors.json`·업종 모델 파일을 함께 배포 |

엔진 파일과 설계서 단계의 대응:

| 단계 | 파일 |
|---|---|
| 1 상황 파악 (일정·반복 구간·업종 예측·금액·브랜드) | `engine/scenarios.py`, `engine/category_model.py`, `engine/priors.py` |
| 2 사용자 규칙 · 일정 행사 카드 | `engine/rules.py`, `engine/service.py` (`_promotion_card`) |
| 일정 팝업 (카드 추천 · 행사 추천) | `engine/popup.py`, `engine/recommend.py` |
| 3 실적 채우기 방식 | `engine/strategy.py`, `engine/strategy_store.py` |
| 4 기본 카드 | `engine/ranker.py` (`choose_base`) |
| 5 원화 점수 (즉시 혜택 + 프로모션 기대값) | `engine/ranker.py` (`score_cards`, `promotion_value`), `engine/benefit_calc.py` |
| 6 교체 판단 | `engine/ranker.py` (`v4_swap`), `engine/perf_value.py` (`switch_threshold`) |
| 안내 문구 · 예시 거래 | `engine/messages.py`, `engine/example.py` |
| 하루 시간표 | `engine/day_plan.py` |
| 사용자 상태 · 기준값 | `engine/state.py`, `engine/params.py` |
| 진입점 | `engine/service.py`, `engine/api.py` |
| 데이터 읽기 | `engine/team_db.py`(팀 DB 형식 CSV), `engine/db_store.py`(PostgreSQL), `engine/store.py`·`engine/pg_store.py` |
| 맞춤 추천 페이지 · 월간 리포트 · 놓친 혜택 | `engine/page.py`, `engine/report.py`, `engine/service.py` (`missed_benefit`) |
| 일정 직접 입력 분류 | `engine/place.py`, `engine/chat/place_llm.py` |
| 개인정보 가리기 · 일정 암호화 · 매일 작업 | `engine/privacy.py`, `engine/crypto.py`, `engine/jobs.py` |

`engine/benefit_calc.py` 는 가상 데이터 생성기 `data/generate/benefit.py` 와 글자까지 같은 파일이다. 한쪽을 고치면 다른 쪽도 고친다 (`tests/test_real_data.py` 가 차이를 잡는다).

## 2. 데이터

서버는 팀 DB 형식(23개 표, 팀 `schema.sql` 과 같은 칸)을 읽는다. 지금 쓰는 데이터는 **v2.1** 이다.

| 항목 | 내용 |
|---|---|
| 폴더 | `카드서비스_DB_1년_v2.1` (저장소 루트, 깃 제외) |
| 카드·혜택 | 44장 (신한 18 · KB국민 6 · 하나 6 · BC 5 · NH농협 5 · 롯데 4), 혜택 311개·구간별 762행 |
| 업종·가맹점·행사 | 업종 58, 가맹점 660, 별칭 21, 행사 29건 (마이샵 23 · 이벤트 6) |
| 고객·결제 | 가상 고객 1,005명 (시연 계정 1~5번), 2025-11-01 ~ 2026-11-26 결제 1,129,900건 |
| 학습 산출물 | `artifacts/v2.1` (업종 모델 `category_lgbm.txt`·`category_classes.json`, 전체 분포 `priors.json`) |

- 엔진이 읽는 표: cards, card_tiers, benefits, benefit_tiers, benefit_targets, benefit_groups, benefit_group_tiers, categories,
  merchants, merchant_aliases, users, user_cards, user_card_details, payments, payment_details, promotions (+ 챗봇 안내용 card_perks).
- 카드 코드·카드사 코드·브랜드 표기 규칙은 설정 `data/config/card_db_map.yml` 을 읽는다.
- 결제(`payments.merchant_name`, 브랜드 단위)는 (브랜드, 업종)마다 대표 지점에 잇고, 지점이 없는 온라인·동네 가맹점은 10,000,001 부터 번호를 붙인다.
- 타사 카드 결제는 마이데이터로 다음 날 반영된다고 보고 그때까지 실적에 넣지 않는다.

## 3. 처음 실행

[uv](https://docs.astral.sh/uv/) 가 필요하다.

```bash
cd solpay-ai
uv sync
cp .env.example .env            # OPENAI_API_KEY 등을 채운다
uv run pytest
```

v2.1 데이터로 서버 켜기 (`SOLPAY_ARTIFACTS` 는 서버를 켤 때 환경 변수로 준다. `.env` 로는 정할 수 없다):

```bash
# DB 없이 CSV 를 메모리에 올려 쓰기
SOLPAY_STORE=teamdb SOLPAY_TEAM_DB_DIR=../카드서비스_DB_1년_v2.1 SOLPAY_ARTIFACTS=artifacts/v2.1 \
  uv run uvicorn engine.api:app --port 8000

# 로컬 PostgreSQL (solpay_v21) 을 읽기
POSTGRES_DB=solpay_v21 SOLPAY_ARTIFACTS=artifacts/v2.1 uv run uvicorn engine.api:app --port 8000
```

`SOLPAY_DEV_TOOLS=on` 이면 http://127.0.0.1:8000/dev (시험 화면) 와 `/docs` (API 직접 호출) 가 열린다.

## 4. 학습

```bash
# 전체 사용자 분포 (금액·브랜드 비중 등, --until 전 결제)
uv run python -m training.build_priors

# 업종 예측 LightGBM: 2026-01~06 으로 학습, 07~10월로 평가 → artifacts/category_*.{txt,json}
uv run python -m training.train_category

# 실적 채우기 방식 선택 모델 / 남은 소비 예측 모델 (기본으로 쓰지 않음. 서버는 SOLPAY_ML=on 일 때만)
uv run python -m training.train_strategy
uv run python -m training.train_spend

# 기준값 후보 비교 (설정은 바꾸지 않는다)
uv run python -m training.tune
```

업종 모델 설정: 학습률 0.03, 잎 31, 잎 최소 데이터 40, 특성 비율 0.7, L2 20, max_bin 63, 조기 종료 30회.
v2.1 결과(07~10월 195,142건): 1순위 적중 52.2%, 3순위 75.6%, 로그 손실 1.624 (`artifacts/v2.1/category_metrics.json`).

## 5. 평가

```bash
# 습관 대비 엔진 혜택률 (재생: 결제를 시간순으로 다시 흘리며 그 시점 정보로만 배치)
uv run python -m evaluation.replay --start 2026-07 --schedule --popup --choice first

# 사후 최적 상한 (결제를 모두 미리 알 때의 최대 혜택)
uv run python -m evaluation.oracle

# 같은 엔진이 결제를 미리 안다고 할 때 (예측 오차만 뺀 값)
uv run python -m evaluation.replay --upper-bound

# 조건 바꿔 보기
uv run python -m evaluation.replay --schedule --schedule-special 0.5 --schedule-normal 0.2   # 일정 입력 비율
uv run python -m evaluation.replay --myshop-on 1                                             # 마이샵을 모두 켰다고 볼 때
uv run python -m evaluation.replay --category-model v1                                       # 업종 예측을 시간대 빈도로
uv run python -m evaluation.replay --base-order main_top                                     # 방식 고정 (first_tier·main_top·value·auto·top_tier)
uv run python -m evaluation.replay --accept 0.7                                              # 추천을 70% 만 따를 때

# 데모 사용자 보고서 (결제별 CSV 는 artifacts/reports)
uv run python -m evaluation.demo_report --user 1

# 실제 OpenAI 를 부르는 평가 (질문마다 비용이 든다)
uv run python -m evaluation.chat_eval                 # 챗봇 83문항
uv run python -m evaluation.chat_eval_500 run         # 챗봇 500문항 (build·report 명령은 6장)
uv run python -m evaluation.place_eval                # 일정 직접 입력 분류 69개 (--no-llm 이면 검색만)
uv run python -m evaluation.page_eval                 # 맞춤 추천 페이지 문구
uv run python -m evaluation.report_eval               # 월간 리포트 문구 (데모 1~5번)
```

재생 평가 옵션: `--start`·`--until`(기간), `--choice`(`best_shown` 화면 카드 중 최대 / `first` 1순위로 결제), `--schedule`(평소와 다른 결제 30%·일반 10% 를 일정으로 입력),
`--popup`(일정 팝업), `--promotion-source`(`db` 기본), `--myshop-on`(습관 결제의 마이샵 ON 비율, 기본 0.3), `--no-promotions`, `--switch`, `--engine`.

현재 결과 (v2.1, 1,005명, 2026-07-01 ~ 11-05, 결제 202,288건, 일정 입력·팝업·행사 29건, 마이샵 30%):

| 항목 | 결과 |
|---|---|
| 혜택률 | 엔진 **1.326%** · 습관 0.811% (+0.515%p), 1인 월평균 8,205원 더 받음 |
| 상한 | 예측 완벽 1.528%, 사후 최적 1.536% → 확보율 71.1% |
| 사람별 | 더 받음 964명, 같음 4명, 손해 37명 (합 −180,670원) |
| 규칙 점검 | 45명·배치 9,361건, 문제 0건 |
| 속도 (엔진 계산) | 중앙 4.5ms, 95% 11.4ms, 99% 18.9ms |
| 챗봇 500문항 | 495/500 (99.0%), 응답 시간 중앙 7.1초 |
| 일정 직접 입력 분류 | 업종 95.7%, 브랜드 100%, 틀린 브랜드 0 |

## 6. 챗봇

- 앱 → 백엔드 `POST /api/ai/chat` → `POST /internal/chat` → OpenAI(GPT-6.1 Terra, Chat Completions 함수 호출, 생각 단계 none).
- 금액·혜택·실적 숫자는 모두 도구가 계산하고 LLM 은 문장만 쓴다. 서버는 대화를 기억하지 않고 DB 에 쓰지 않는다 (규칙 초안만 app 스키마에 '대기'로).
- 자세한 구조·도구·검사·실패 처리는 `docs/설계/LLM_챗봇_설계서.md`.

```bash
curl -s -X POST http://127.0.0.1:8000/internal/chat -H 'Content-Type: application/json' \
  -d '{"user_id": 1, "message": "스타벅스에서 6천 원 결제할 건데 뭐 써?", "screen": {"name": "pay"}}'
```

| 파일 | 역할 |
|---|---|
| `engine/chat/agent.py` | OpenAI 호출, 도구 반복(질문당 3번), 15초 제한, 검사 실패 시 한 번 다시 쓰기, 예비 답변 |
| `engine/chat/tools.py` | 도구 17개 정의(JSON 스키마)·실행, 화면 요소(blocks), 규칙·일정·규칙 지우기 초안 |
| `engine/chat/prompts.py` | 시스템 프롬프트(역할·숫자 원칙·도구 사용·앱 사용 안내·카드 용어·답변 형식·금지 사항)와 문맥, `PROMPT_VERSION` |
| `engine/chat/guard.py` | 숫자 검사(도구 결과에 없는 금액·비율), 소비 권유·저장 주장·초안 없는 저장 안내 검사 |
| `engine/chat/history.py` | 결제 기록 합계·지난 결제 다시 계산·받은 혜택 |
| `engine/chat/search.py`, `new_card.py` | 카드·가맹점(별칭 포함)·업종 찾기, 새 신한카드 추천 |
| `engine/chat/openai_params.py` | 모델·생각 단계 (`OPENAI_REASONING_EFFORT` 를 빈 값으로 두면 생각 단계 대신 온도를 보냄) |

| 묶음 | 도구 | 화면 요소 |
|---|---|---|
| 지금 결제 | `explain_ranking`, `simulate_payment`, `recommend_for_payment`, `get_day_plan` | `score_table`, `card_compare`, `pay_button` |
| 카드 | `get_card_status`, `get_card_benefits`, `compare_cards` | `card_status`, `benefit_list` |
| 결제 기록 | `get_spending`, `review_payments`, `get_benefit_summary` | 결제 요약·다시 보기·받은 혜택 표 |
| 추천·행사 | `recommend_new_card`, `list_promotions`, `find_merchant` | `new_card_list`, 행사 목록 |
| 규칙·일정 | `draft_rule`, `list_my_rules`, `draft_rule_delete`, `draft_schedule` | `rule_card`, 규칙 목록, `rule_delete_draft`, `schedule_draft` |

규칙 초안 흐름: `draft_rule` 이 초안을 만들면 `POST /internal/chat` 이 `app.chat_rule_drafts` 에 '대기'로 두고 `rule_draft.draft_id` 를 준다 →
사용자가 '저장'을 누르면 `POST /internal/rules/drafts/{id}/confirm` 이 다시 검사(`/internal/rules/validate` 와 같음)하고 `app.user_rules` 에 더한다 (다른 사용자 404, 이미 처리 409). '취소'는 `…/cancel`.

평가:

```bash
uv run python -m evaluation.chat_eval                         # 83문항, 데모 1번
export SOLPAY_TEAM_DB_DIR=../카드서비스_DB_1년_v2.1 SOLPAY_ARTIFACTS=artifacts/v2.1
uv run python -m evaluation.chat_eval_500 build               # 500문항 질문 셋 → evaluation/chat_cases_500.json
uv run python -m evaluation.chat_eval_500 run --users 1       # 사용자별로 나눠 동시에 돌릴 수 있다
uv run python -m evaluation.chat_eval_500 report              # → evaluation/results/chat_eval_500_<날짜>.{json,md}
```

평가는 문항마다 저장소를 초기화하므로 CSV 저장소(`SOLPAY_STORE=teamdb`)로 돈다 (개인 DB 의 app 표를 지우지 않게).

## 7. API

모든 `/internal/*` 는 `SOLPAY_INTERNAL_TOKEN` 을 설정하면 `X-Internal-Token` 헤더를 검사하고, 설정하지 않으면 같은 컴퓨터에서 온 요청만 받는다. 시각(`at`)에 시간대가 없으면 한국 시간으로 본다.
전체 명세는 `openapi.json` (`uv run python -m scripts.export_openapi` 로 다시 만든다).

| API | 하는 일 |
|---|---|
| `POST /internal/rank` | 카드 순서·안내 문구·예시 거래. 본문 `user_id`, `at`, `explain`(판단 근거 포함), `record`(기본 true, 앱 홈 미리보기는 false 로 추천 기록을 남기지 않음). 등록 카드가 없으면 `cards=[]`·`reason_code=NO_CARD`. 일정을 읽지 못하면 일정 없이 소비 패턴으로 배치 |
| `POST /internal/users/{id}/day-placement` | 오늘 시간대별 1순위 카드 (홈 '오늘의 카드 시간표'). 매시 정각·일정 경계에서 계산해 같은 카드 구간을 합침, 기록 없음 |
| `PUT·GET·DELETE /internal/users/{id}/schedules/{day}` | 하루 일정 (시작·끝, 업종, 예상 금액, 선택 칸 `brand`). 암호문으로 저장, 지난 날은 매일 지움 |
| `POST /internal/places/classify` | 일정 '직접 입력'의 짧은 말("스벅", "헬스장")을 업종·브랜드로. 가맹점·별칭·업종 검색 먼저, 못 찾으면 OpenAI 가 목록 안에서 고름, 확신이 낮으면 후보만. 입력 원문은 저장하지 않음 |
| `POST /internal/users/{id}/schedule-popup` | 일정 저장 뒤 팝업: 3일마다 월 3,000원 이상 이득인 새 신한카드(`kind=card`), 그 외 날은 일정 업종 행사 최대 2건(`kind=promotion`). 행사를 추천한 일정 시간에는 그 행사의 신한카드가 1순위 |

## 9. DB

엔진과 챗봇은 DB 주소가 있으면 PostgreSQL 을 읽는다 (`engine/db_store.py`).

| 구분 | 내용 | 누가 쓰나 |
|---|---|---|
| 팀 23개 표 (public) | 팀 `schema.sql` + 데이터 | AI 서버는 **읽기만** |
| 쓰기용 표 (app) | `sql/002_app.sql`: 규칙, 규칙 초안, 실적 채우기 방식, 추천 기록, 하루 일정(암호문), 새 카드 추천 기록, 시연 결제 | AI 서버 |

- 카드·혜택·가맹점·행사·업종 표는 서버 시작 때 한 번, 사용자·보유 카드·결제는 요청마다 그 사용자 것만(최근 400일) 읽는다. 연결은 `psycopg_pool` 로 재사용한다.
- 결제 화면 요청은 DB 에 쓰지 않는다(추천 기록 제외). 지난 날 일정은 서버 시작 때와 매일 00:05(한국 시각)에 지운다 (`engine/jobs.py`). 실패해도 서버는 멈추지 않고 경고만 남긴다.
- 결제 조회 인덱스가 필요하다: `CREATE INDEX ON payments (user_card_id, paid_at);`
- 공동 DB 를 쓰는 AI 서버들은 같은 `SOLPAY_DATA_KEY` 를 써야 서로 저장한 일정을 읽는다.

로컬 DB 준비 (여러 번 실행해도 된다):

```bash
# 저장소 루트: PostgreSQL 켜기 (Docker Desktop, 계정은 루트 .env)
docker compose up -d db
# solpay-ai: 팀 표가 없으면 schema.sql + CSV 적재, 있으면 행 수 대조. app 스키마 생성. 일정 키가 없으면 .env 에 만든다
uv run python -m scripts.setup_local_db --team-dir ../카드서비스_DB_1년_v2.1 --db solpay_v21
uv run python -m scripts.setup_local_db --db solpay_test      # 자동 시험용 DB (tests/test_db_store.py)
```

공용 DB 에 붙일 때:

1. 공용 DB 에 팀 `schema.sql` 로 23개 표를 만들고 데이터를 적재한다 (팀 절차).
2. `solpay-ai/.env` 에 `SOLPAY_DATABASE_URL` 을 넣는다. AI 서버 계정은 public 읽기, app 쓰기 권한이면 된다.
3. 공용 DB 에 `sql/002_app.sql` 을 적용한다.
4. 스키마 이름이 다르면 `SOLPAY_TEAM_DB_SCHEMA`·`SOLPAY_APP_SCHEMA` 로 맞춘다.
5. 위 결제 인덱스를 만든다.

## 10. 행사(카드사 이벤트·마이샵)

- 원본은 DB `promotions` 표 하나다. 앱 혜택 탭(백엔드 `/api/promotions`)과 챗봇·추천·배치가 같은 표를 읽는다.
- 점수 기간은 `start_date`~`end_date`(1년치 가상 결제용), '지금 진행 중'(맞춤 추천·일정 팝업·챗봇 목록)과 화면 기간은 `display_start`~`display_end`(실제 행사 기간).
- 응모·선착순 조건(`needs_check`) 행사는 점수와 챗봇 목록에서 뺀다. 브랜드도 업종도 없는 행은 어느 가맹점에도 적용하지 않는다.
- 응답에는 화면 이름(`display_name`)과 로고(`logo_url`)를 싣는다. 화면용 칸이 없는 데이터는 `data/config/promotions.yml` 에서 같은 번호로 채운다.
- 결제 한 건에는 행사 하나(가장 큰 것)만 붙고, 행사는 신한카드 결제에만 붙는다.

## 11. 하루 일정과 개인정보

- 위치(GPS)는 쓰지 않는다. 결제 화면은 일정이 있으면 일정(시작 30분 전 ~ 끝 30분 후), 없으면 소비 패턴으로 배치한다.
- 일정은 시작·끝 시각, 업종, 예상 금액(앱이 안 주면 백엔드가 내 업종 결제 중앙값 → 전체 중앙값 → 10,000원), 선택 칸 브랜드만 받고 장소·메모는 받지 않는다.
- 일정 시간에 같은 업종 현장 결제가 이미 있으면 그 일정은 끝난 것으로 본다. 오늘 남은 일정이 있으면 남은 예상 결제를 그 일정의 합으로 대신한다.
- 암호화 키: 로컬은 `.env` 의 `SOLPAY_DATA_KEY`
  (`uv run python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"`), 운영은 KMS 로 암호화한 데이터 키 `SOLPAY_DATA_KEY_ENCRYPTED` + `SOLPAY_KMS_KEY_ID`.
- OpenAI 로 보내는 값은 `engine/privacy.py` 를 거친다: 사용자 문장 속 카드번호·계좌번호·주민등록번호·전화번호·이메일을 가리고(`redact`, 한글에 붙여 쓴 번호 포함),
  엔진 결과는 카드 상품명·업종·금액·구간만 남긴다(`llm_view`). 사용자 번호·이름·가맹점 원문·일정 원문은 보내지 않는다.

## 12. 시스템 연동

1. **호출**: 앱은 백엔드만 부르고, 백엔드가 `/internal/*` 를 부른다. 배치는 제한 2초(`AI_RANK_TIMEOUT_MS`), 넘거나 오류면 백엔드가 사용자 카드 표시 순서로 응답한다(`reason_code=FALLBACK`). 챗봇 등은 20초(`AI_TIMEOUT_MS`), 일정 분류 3초(`AI_CLASSIFY_TIMEOUT_MS`).
2. **토큰**: 운영에서는 `SOLPAY_INTERNAL_TOKEN` 을 설정해 백엔드만 부르게 한다.
3. **결제**: 백엔드가 결제를 저장하고, 엔진은 DB 를 읽어 요청마다 상태를 다시 만든다.
4. **배포**: 이미지에 `engine/` 과 `artifacts/v2.1` 의 `priors.json`·`category_lgbm.txt`·`category_classes.json` 을 넣고 `SOLPAY_ARTIFACTS` 로 가리킨다.
5. **기준값**: `engine/params.py` 에서 바꾼다. 공휴일 목록(`Params.holidays`)은 운영 달력으로 바꾼다.

## 13. 포함하지 않은 것

- 행사의 기간 누적 한도와 1인 횟수 제한 (건당 한도만 계산).
- 사용자의 실제 마이샵 ON 상태 (행사 때문에 고른 카드면 문구에 행사 이름을 보여 줘 켜도록 안내).
- K-패스 정부 환급 (카드사 혜택만 계산).
- 겹친 일정 고르기, 일정별 결제 연결·취소 처리.
- 챗봇 하루 질문 수 제한, 대화 기록 보관 기간 (백엔드 몫).
- 평가의 일정 입력 비율(평소와 다른 결제 30%·일반 10%)과 마이샵 ON 30% 는 가정값이다.
