# 가상 소비 데이터 생성기

> **이 데이터는 카드 배치 알고리즘을 구축할 때 쓰는 사용자의 과거 소비 데이터다.**
> 알고리즘은 배치 시각 이전의 결제만 입력으로 쓸 수 있고, 학습과 평가는 시간순으로 나눈다.
> 생성기 전용 정답 컬럼(`payments.choice_reason` 등)은 입력으로 쓰지 않는다.

최종 카드 DB의 카드 40장(신한 14, KB국민 6, 하나 6, BC 5, NH농협 5, 롯데 4) 중 2~4장을 가진 사용자 365명(데모 5 + 배경 300 + 50대 60)이 2025-11-01부터 2026-11-05 10:00까지 결제한 내역을 만든다. 2026-11-14 데이터 점검에 따라 카드 발급일(데이터 시작 전), 전기차 충전·광역교통·간편결제 등 업종 추가, 페르소나별 차량 보유, 소비 배율 상한 2배, 시간대 정규분포, 학원비 자동이체를 반영했다.
카드 혜택·실적 구간·한도는 최종 카드 DB 표(`config/card_db/*.csv`, 원본 `~/Downloads/카드서비스_DB`)를 그대로 쓰고, 카드 코드·해외 혜택 제외·브랜드 표기 맞춤은 `config/card_db_map.yml` 에 둔다 (2026-11-15). 신한카드는 모든 사용자가 1장 이상, 60%는 타사 카드도 가진다.
업종은 최종 카드 DB의 58개 코드를 쓰고, 그중 생활 업종 44개에 결제를 만든다. 결제는 가상이다.
사용자는 혜택과 무관한 습관으로 카드를 고르며, 혜택은 그 결제 내역 위에서 계산한다.

## 실행

```bash
cd data
uv sync                              # 처음 한 번
uv run python -m generate.main       # 생성 (5초 안팎)
uv run python -m generate.summary    # 숫자 확인
uv run pytest                        # 검증
```

같은 `seed`(config/settings.yml)면 누가 돌려도 같은 결과가 나온다. 결과물(`out/`)은 깃에 올리지 않고 각자 다시 만든다.

### v2 (1005명, 2026-11-22)

직업·나이대가 비슷한 사용자끼리 학습할 수 있게 만든 판이다. 같은 코드에 `config/v2/*.yml` 을 기본 설정 위에 겹쳐 쓴다(사전은 합치고 목록은 바꿈).
배경 1000명 = 직업 10개(사무직·대학생·맞벌이·야근·재택·전업주부·자영업·교대근무·영업외근·은퇴) × 20~60대 26칸(칸마다 30명 이상) + 데모 5명(카드 3~5장).
같은 직업 안에서도 나이대마다 업종 비중·건당 금액·차량·학원비가 다르다(`age_effects`, 배경 사용자만). 기간·시드·표 형식은 v1 과 같다.
설계: `docs/superpowers/specs/2026-11-22-data-v2-1000-design.md`

```bash
SOLPAY_DATA_VERSION=v2 uv run python -m generate.main        # → out_v2/ (45초 안팎)
SOLPAY_DATA_VERSION=v2 uv run python -m generate.summary     # 직업×나이대 표 포함
SOLPAY_DATA_VERSION=v2 uv run python -m generate.export_db   # → ../카드서비스_DB_1년_v2 (v1 폴더에는 쓰지 않음)
uv run pytest tests/test_generated_v2.py                      # v2 검증 (환경 변수 없이)
```

### v2.1 (v2 + 개인 루틴, 2026-11-23)

v2 는 업종을 직업·나이대 확률로 결제마다 새로 뽑아 "평일 8시 반엔 꼭 커피" 같은 개인 루틴이 없었다. 개인 습관 가중치를 시험하려고
배경 사용자 절반에게 직업에 맞는 루틴 1~2개(출근길 커피·점심 식당·퇴근길 편의점 등)를 넣은 판이다. 점이 있는 판은 큰 판 설정 위에
한 번 더 겹친다(`config/v2` → `config/v2.1`). 루틴은 정해진 시각 ±30분, 해당 요일 60~90% 확률로 지킨다. 그날의 같은 종류 결제나
금액이 비슷한 결제를 루틴으로 바꾸고, 없을 때만 새로 만들고 뒤의 날 결제를 빼서 결제 수(+2%)와 월 지출(+0.4%)을 v2 와 비슷하게 둔다.
루틴은 따로 뽑은 난수로 정해서 루틴이 없는 사용자의 결제는 v2 와 똑같다. 루틴 목록은 `user_routines`·`routine_events`
(생성기 전용, 팀 DB 에는 넣지 않음). 사용자·카드·팀 DB 의 사용자 표는 v2 와 같다.

```bash
SOLPAY_DATA_VERSION=v2.1 uv run python -m generate.main       # → out_v2.1/
SOLPAY_DATA_VERSION=v2.1 uv run python -m generate.export_db  # → ../카드서비스_DB_1년_v2.1
uv run pytest tests/test_generated_v2_1.py                     # v2.1 검증
```

## 카카오 실제 가맹점 위치 (선택)

1. Kakao Developers에서 앱을 만들고 REST API 키를 받는다.
2. `.env.example`을 `.env`로 복사하고 `KAKAO_REST_API_KEY`를 채운다.
3. `uv run python -m generate.kakao_fetch` → `cache/kakao_places.csv` (`--kinds SALAD,DEPT` 로 일부 종류만 다시 받기)
4. 다시 `generate.main`을 돌리면 가상 좌표 대신 실제 위치를 쓴다.

`cache/`는 카카오 이용약관의 저장·재배포 조건을 확인하기 전까지 깃에 올리지 않는다.

## 제공 데이터 반영 범위

| 항목 | 내용 | 근거 |
|---|---|---|
| 업종별 건당 금액 | 생성 결과의 업종 평균을 맞춤 (`amount`) | 2020년 신한카드 시군구별·온라인소비, 구별 중앙값 |
| 사용자별 지출 격차 | 월 지출 목표 24만 / 107만 / 352만 (`spend_level`) | CreDB 카드 이용 내역. 단위는 천 원으로 가정 |
| 공과금 | 전기·도시가스·아파트 관리비, 건당 금액 수준만 참고 | 월납/세금은 강남구·중구 등록지에 몰려 비중은 쓰지 않음 |
| 데모 3번 | 홈쇼핑 비중, 오전 온라인 비중 | 삼성카드 온라인쇼핑 50대 여성 |

대형마트·슈퍼 금액은 장보기 금액을 반영한 가정값이다 (제공 데이터 평균은 40,100원, 16,500원).

그 밖의 시간대·업종 가중치, 심야 결제, 충동·대형 결제, 단골 확률 범위는 가정값이다.
불규칙 소비는 배경 사용자에게만 넣고, 데모 5명은 시연을 위해 규칙적인 패턴을 유지한다.

## 결과 파일 (`out/parquet`, `out/csv`)

parquet에는 전체가, csv에는 기준 정보와 데모 사용자 5명분만 들어간다.
`payments.choice_reason`(가상 사용자가 카드를 고른 이유)은 생성기 전용이라 csv에서는 뺀다.

| 테이블 | 내용 |
|---|---|
| issuers, merchant_categories, card_catalog | 기준 정보 |
| card_benefits | 카드별 혜택 규칙 (업종, 비율·정액, 건당 최소, 월 횟수, 요일·시각 조건) |
| card_cap_tiers | 전월 실적 구간별 월 혜택 한도. `monthly_cap`이 비어 있으면 한도 없음 |
| merchants | 오프라인 가맹점 동네당 60곳 + 온라인·교통·자동이체 가맹점 |
| users | 사용자, 유형, 동네, 카드 고르는 습관 |
| user_cards | 보유 카드, 기본 순서, K-패스 등록 카드, 교통 대표 카드, 고지서 카드 |
| user_category_habits | 업종별 습관 카드 (직장인·맞벌이·데모 3번). 카드 매칭할 때 쓴다 |
| payments | 결제 내역 |
| card_month_status | 보유 카드별 월 실적, 받은 혜택, 결제 건수 |
| promotions | 이벤트·마이샵 혜택. 브랜드, 카드사, 기간, 정액·비율, 건당 최소·최대 금액, 확인 필요 여부. 가맹점 매칭은 엔진이 브랜드명으로 한다 |

`card_month_status`의 `prev_perf`만 그달 초에 알 수 있는 값이다. `perf`와 `benefit_amount`는 월말 합계이므로, 배치 시각의 당월 실적은 그 시각 이전 `payments`로 계산한다.
첫 달인 7월은 전월 실적이 없어 혜택 없이 실적만 쌓고, 11월은 기준 시각까지의 값이다. 실적에는 모든 결제가 들어간다.

## 카드 상품 수집기 (collector/)

카드사 공식 홈페이지의 공개 상품 상세 페이지에서 카드 정보와 혜택을 직접 수집한다.
카드사별 차이(상품 목록 얻는 법, 카드명 위치, 혜택 영역, 렌더링 필요 여부)는 `config/crawl.yml`에 모으고 코드는 공통으로 쓴다.

```bash
cd .. && docker compose up -d && cd data   # DB (레포 루트 .env)
uv run playwright install chromium         # 처음 한 번 (렌더링이 필요한 우리·현대·토스용)
uv run python -m collector discover        # ① 상품 상세 주소 찾기
uv run python -m collector fetch           # ② 원문 수집 (이미 받은 카드는 건너뜀)
uv run python -m collector parse           # ③ 규칙 파서: 카드명·종류·연회비·출시일·대표 혜택 문구
uv run python -m collector structure       # ④ Gemini 구조화: 업종·할인율·시간대·건당/월 한도·실적 구간
uv run python -m collector load            # ⑤ DB 적재
uv run python -m collector report          # 카드사별 결과 요약
```

`--issuer KB`(카드사 지정), `--limit 5`(시험용), `--force`(다시) 옵션이 있다.

**수집 원칙**
- 로그인 없이 공개된 카드사 공식 상품 페이지만 읽는다.
- robots.txt가 허용한 주소만 요청한다. robots.txt가 응답하지 않으면 막힌 것으로 본다.
- 브라우저로 화면을 그릴 때도 robots.txt가 막은 요청과 카드사 도메인 밖 요청은 브라우저 안에서 차단한다.
- 접속 차단을 우회하는 수단은 쓰지 않는다. 막히면 '수집 불가'로 기록한다.
- 같은 사이트에는 2초 간격으로 한 번에 하나씩 요청한다.
- 원문은 `cache/crawl/`에만 두고 깃에 올리지 않는다. 근거(`evidence.jsonl`)에는 주소·시각·해시만 남긴다.

**카드사별 상태 (2026-11-03)**

| 카드사 | 상품 목록 | 비고 |
|---|---|---|
| KB국민, 하나 | 사이트맵 | |
| 우리 | 우리카드가 AI용으로 공개한 `llms.txt` | 상세는 화면을 그려야 함 |
| 현대 | 카드 목록 페이지를 그려서 | |
| 토스뱅크 | 사이트맵 | |
| 신한 | 메인 노출분 + 시드 | 목록 요청 경로(`/mob/`)가 robots.txt 금지 |
| BC, NH농협 | 시드만 | 목록이 보안 프로그램 설치 화면으로 넘어감 |
| 삼성, 카카오뱅크, IBK | 수집 안 함 | robots.txt 불허 |
| 롯데 | 수집 안 함 | 응답 없음·연결 끊김 |

자동으로 목록을 얻을 수 없는 카드사는 `config/crawl_seeds.yml`에 상세 페이지 주소를 적으면 수집한다.
