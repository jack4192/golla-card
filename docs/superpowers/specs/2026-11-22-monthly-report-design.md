# 월간 리포트 설계 (2026-11-22)

## 왜 만드나

금융 AI 시스템 설계 경진대회에서 AI 활용이 약해 보인다. 월간 리포트는 사용자가 한 달 동안 카드별로 무엇을 받았는지, 실적은 어디까지 왔는지,
SOL페이가 어떤 전략으로 카드를 배치했고 그 덕분에 얼마를 더 받았는지를 한 화면에서 보여 준다.
숫자는 엔진이 계산하고 요약 문장은 OpenAI 가 쓰는 원칙("고르는 건 엔진, 문구는 AI")을 그대로 지킨다.
API 명세서 64번 '이번 달 혜택 리포트'(백엔드 미구현, 앱 화면 없음)에 해당한다.

## 사용자 결정 (2026-11-22)

| 항목 | 결정 |
|---|---|
| 요약 문장 | OpenAI 가 쓰고 숫자 검사. 검사에 걸리거나 OpenAI 장애면 정해진 문구 (추천 페이지 문구와 같은 방식) |
| SOL페이 효과 | "지난달 결제를 추천 1순위 카드로 냈다면" 다시 계산한다 |
| 효과 계산 범위 | 지난달 카드 혜택 차이 + 지난달 프로모션 차이 + 지난달 실적이 이번 달 혜택에 주는 차이(추정)를 더한다. 화면에는 셋을 나눠 보여 준다 |
| 덜 받은 사용자 | 숨기지 않고 그대로 보여 주되 이유를 남긴다 |
| 카드별 프로모션 | 카드별로는 보여 주지 않는다 (효과 합계에만 들어간다) |
| 보이는 곳 | AI 서버 API + 개발용 시험 화면(/dev) 탭. 앱 화면은 Spring 연결 때 |
| 카드 배치 전략 | 이번 달 실적 채우기 방식, 고른 근거, 지금 실적을 채우는 카드를 보여 준다 |

## 목표 / 하지 않을 것

- 목표: 카드별 이번 달·지난달 숫자, 전략과 근거, SOL페이 효과(이유 포함), AI 요약을 API 한 번으로 준다.
- 하지 않을 것: 앱(Expo) 화면, Spring 연동, 리포트 저장(DB 쓰기), 알림 발송, 카드별 프로모션 표시, 연말 리포트 변경.
- 실패로 보는 것: 요약 문장에 엔진에 없는 숫자가 들어가는 것, 덜 받은 사용자에게 더 받았다고 말하는 것, 이유 없이 손해만 보여 주는 것.

## API

## 계산

### 카드별 숫자
- 이번 달: 지금 `card_status` 와 같은 상태 재생. 한도는 챗봇 `get_card_status` 의 한도 계산을 공용 함수로 옮겨 같이 쓴다.
  `tier_min` 은 지난달 실적으로 이번 달 받는 구간 하한, `remaining_to_keep` 은 다음 달에도 그 구간을 받기까지 남은 금액,
  `next_tier` 는 이번 달 실적 바로 위 구간.
- 지난달: 지금 보이는 결제 중 이번 달 1일 전 결제만으로 상태를 다시 만든다(늦게 들어온 타사 결제 포함).
  `achieved` = 첫 구간(혜택을 받기 시작하는 최소 실적) 달성 여부, `tier_reached` = 도달한 가장 높은 구간 하한,
  `short_of_first` = 첫 구간까지 모자랐던 금액.
  확인: 1번 사용자 10월 카드별 실적·혜택이 팀 DB `card_month_status` 와 같다 (Discount Plan 1,542,790원·43,220원 등).
- 금액은 엔진이 계산한 카드사 혜택(할인·캐시백·적립)이다. 프로모션은 카드별로 넣지 않는다.
- 실적 조건이 없는 카드(구간이 0원 하나뿐)는 구간 칸을 `null` 로 두고 `achieved: null`.
- `totals` 는 카드별 금액의 합. 이유 코드는 1순위 카드 안내 문구 코드로 묶는다: RULE → 사용자 규칙, PROMOTION·PROMOTION_CARD → 프로모션,
  PERFORMANCE·HOLD·BASE_CHANGED → 실적 채우기, 나머지 → 혜택 비교.
- OpenAI 키가 없으면 바로 정해진 문구(`copy_source: template`).

### 카드 배치 전략
- 챗봇 `explain_ranking` 의 이번 달 방식 안내(`_month_strategy`)를 서비스 함수로 옮겨 리포트와 챗봇이 같이 쓴다.
  우선순위: 사용자 규칙(order) → 사용자 확정 → 월간 맞춤(최근 6개월 결제를 방식마다 다시 돌린 혜택 비교) → 기본 방식.
- 방식 설명은 `params.py` 정의를 그대로 쓴다: 첫 구간 우선(모든 카드의 첫 구간 먼저), 주력 카드 우선(구간 혜택이 가장 큰 카드의 높은 구간부터),
  가치 최대(예산 안에서 구간 증분 혜택 − 포기하는 혜택이 최대인 조합), 실적 안 채움(결제마다 혜택률 1위), 1번 카드 최고 구간 우선.
- 지금 실적을 채우는 카드와 결제 화면 순서·안내 문구는 기록을 남기지 않는 `preview(user, at)` 로 구한다.
  `base_card` 는 그 카드의 이번 달 구간 칸(`tier_min`·`remaining_to_keep`·`next_tier`·`remaining_to_next`, 카드별 숫자와 같은 값).
- 엔진(`ranker.choose_base_card`)은 구간 지키기를 어느 방식보다 먼저 적용한다. 그래서 기본 카드를 구간 지키기로 정했으면
  `base_reason` = "어느 방식이든 지난달 받은 구간을 지킬 수 있으면 그 카드를 먼저 채워요", 아니면 `null` (방식 설명과 기본 카드가 어긋나 보이지 않게).

### SOL페이 효과 (지난달)
- 지난달 1일 기준 상태 세 벌(실제·추천·엔진이 보는 상태)에서 지난달 결제를 시간순으로 다시 흘린다 (재생 평가 `replay_user` 를 한 달로 줄인 것).
  결제화면을 연 결제(`is_placement`)만 엔진 1순위 카드로 바꾸고, 나머지(온라인·자동이체·교통)는 실제 카드 그대로.
  엔진이 보는 상태는 동기화 시각(`visible_at`) 이후에 결제를 안다. 규칙은 지금 규칙, 일정·일정 팝업은 쓰지 않는다.
- card = 각 결제로 받은 카드 혜택 합. promotion = 그 결제·카드에 걸리는 진행 중 행사 중 가장 큰 것 (실제·추천 같은 조건으로, 마이샵은 켰다고 본다).
- next_month = 지난달 카드별 결제를 지난달 실적 구간으로 이번 달에 똑같이 했다면 받을 혜택 추정 (`strategy.month_benefit`, 월간 맞춤 방식과 같은 추정).
- total = card + promotion + next_month 의 차이. 음수여도 그대로 준다.
- 이유: `top_changes` = 추천과 실제 카드가 달랐던 결제 중 차이(카드 혜택+프로모션)가 0원이 아닌 것에서 큰 순 3건 (덜 받은 결제 우선, 엔진 이유 코드를 '실적 채우기/프로모션/혜택 비교/사용자 규칙'으로),
  `tier_changes` = 실제와 추천의 실적 도달 구간(`actual_tier`·`recommended_tier`, 못 닿으면 `null`)이 다른 카드. `direction` 은 추천대로면 더 높은 구간 `up`, 더 낮은 구간 `down`.
- 결제화면을 연 결제가 지난달 없으면 `solpay_effect: null` 과 `effect_note` 를 준다.
- 사전 측정 (10월, 표본 60명): 중앙값 +3,735원, 덜 받은 사람 10명 (최소 −14,500원, 최대 +50,200원). 한 사람 0.1~0.3초.

### 요약 문장 (OpenAI)
> 이 절과 아래 '확인 방법'의 요약 문장 부분은 끝의 두 변경 절('효과 문장은 엔진이 쓴다', '전략 문장도 엔진')로 바뀌었다.
> 지금은 OpenAI 가 제목과 카드 숫자 요점만 쓰고, 효과·이유·배치 전략 문장은 엔진이 쓴다. 아래는 처음 설계 기록으로 남긴다.

- 새 파일 `engine/chat/report_copy.py`: `facts_of(report)` → OpenAI(`OPENAI_MODEL`, 기본 gpt-4o-mini, JSON `{headline, points}`, points 최대 3개)
  → 검사 → 걸리면 한 번 다시 쓰기 → 그래도 걸리면 `template_copy`. 제한 시간 `REPORT_COPY_TIMEOUT_SEC` 기본 8초.
- OpenAI 에 보내는 사실: 카드 상품명, 업종 이름, 금액, 날짜(일 단위), 방식 이름. 가맹점 이름·사용자 이름은 보내지 않는다.
- 사실에는 덜 받은 값의 양수도 넣는다 (`shortfall`, `less_by_part`, `top_changes[].less`. '300원 덜'이 숫자 검사를 통과하게),
  `tier_changes[].direction`, 기본 카드 이유 `strategy.base_reason`.
- 덜 받은 이유는 엔진이 하나 고른다 (`effect.reason`, 사실과 글자 그대로 맞는 것만): 추천대로면 도달 구간이 내려간 카드(`tier_down`)
  → 없으면 가장 많이 덜 받은 결제(`payment`) → 둘 다 없으면 가장 많이 줄어든 항목(`part`). LLM 은 그 하나를 문장으로만 쓴다.
- 검사: 문장 속 숫자는 사실에 있는 값만 (만 원 단위 반올림 '약 5만 원' 허용), total 이 음수면 '더 받았다'류 표현 금지 + 덜 받은 금액과 이유 하나 이상 언급,
  양수면 '덜 받' 금지, 0 이면 '더 받'·'덜 받' 모두 금지, 저장·설정 주장 금지(챗봇 검사기 재사용).
- 정해진 문구 예 (0이 아닌 항목은 모두 부호와 함께, 합이 total): "10월에 카드 혜택 47,070원을 받았어요." /
  "추천대로 냈다면 5,180원을 더 받을 수 있었어요(10월 카드 혜택 +290원, 실적 덕분에 11월 +4,890원 예상)." /
  덜 받은 경우 "추천대로 냈다면 7,350원 덜 받았어요(10월 카드 혜택 +2,230원, 10월 프로모션 +1,050원, 실적 차이로 11월 -10,630원 예상)."
  + 이유 "추천대로였다면 NH농협 zgm 할인 실적이 410,500원에서 273,450원으로 줄어 40만 원 구간을 놓쳤어요." (구간이 내려간 카드)
  / "10월 25일 헬스앤뷰티(올리브영 등) 결제를 BC 케이퍼스트 카드로 냈다면 14,170원 덜 받았어요(추천 이유: 혜택 비교)." (가장 많이 덜 받은 결제)
  / "추천대로였다면 10월 카드 혜택이 11,930원에서 11,820원으로 줄었어요." (가장 많이 줄어든 항목)

### 개발용 화면
`/dev` 에 '5. 월간 리포트' 탭: 사용자·시각 입력 → 요약, 카드 표(이번 달/지난달), 전략과 비교 점수, SOL페이 효과와 이유.

## 확인 방법
> 요약 문장 검사·정해진 문구는 끝의 두 변경 절이 정한 것이 우선이다 (효과·전략 문장은 엔진, OpenAI 문장 검사는 효과·전략 표현 금지).

- 자동 테스트: 지난달 구간 계산(달성/미달/첫 구간 모자란 금액), 효과 부호와 합(덜 받은 경우 포함), 이유 정렬, 검사기(모르는 숫자·음수인데 '더 받았다'),
  정해진 문구, API 404·캐시, 팀 DB CSV 로 1번 사용자 10월 숫자가 `card_month_status` 와 같은지(CSV 없으면 건너뜀).
- `evaluation/report_eval.py`: 실제 OpenAI 로 데모 사용자 1~5 × 2026-11-05 리포트 — LLM 통과 수, 다시 쓴 수, 응답 시간. 표본 60명 효과 분포도 출력.

## 내가 정한 것 (사용자 확인 필요)
1. 리포트 기준은 `at` 하나: 이번 달(진행 중) + 지난달(확정). 지난 달 리포트는 `at` 을 그 달로 주면 된다.
2. "지난달 실적 달성" = 첫 구간 달성 여부 + 도달한 가장 높은 구간. `user_cards.target_tier_id`(목표 구간)는 엔진이 쓰지 않아 쓰지 않는다.
3. 효과 계산의 프로모션은 실제·추천 모두 "조건이 맞으면 받았다"고 본다 (DB 의 실제 프로모션 기록과 섞지 않는다).
4. 효과 계산에 지금 규칙을 쓴다 (지난달에 규칙이 달랐을 수 있다).
5. OpenAI 에 가맹점 이름을 보내지 않고 업종 이름만 보낸다.
6. 리포트는 저장하지 않고 하루 단위 메모리 캐시만 둔다.

## 변경 (2026-11-22 저녁): 효과 문장은 엔진이 쓴다

데모 사용자 4번(효과 +8,550원)에서 OpenAI 가 사실 속 숫자를 섞어 거짓 이유를 썼다

숫자 하나하나는 사실에 있어 검사기가 잡지 못했다.

**사용자 결정:** 더 받은 금액·덜 받은 금액·그 이유는 엔진이 정해진 문장으로 쓰고, OpenAI 는 제목과 카드·전략 요점만 쓴다.

- 응답 `summary` = `{"headline": OpenAI, "effect": [엔진 문장 0~2개], "points": [OpenAI 문장 1~2개]}`. 앱은 effect 다음에 points 를 보여 준다. (내 판단: 어느 문장이 엔진이고 어느 문장이 AI 인지 응답에서 구분)
- OpenAI 에 보내는 사실에서 `solpay_effect` 를 뺀다 (효과 숫자를 섞을 수 없게). 검사기는 OpenAI 문장에 효과 표현('추천대로', '더 받', '덜 받', '놓쳤', '구간에 올라')이 있으면 걸러 낸다.
- 엔진 효과 문장 (모두 그 사용자의 데이터에서 글자 그대로 참이어야 한다):
  - 금액 문장: 더 받음 "추천대로 냈다면 {total}원을 더 받을 수 있었어요({0 아닌 부분을 부호와 함께})" / 덜 받음 "추천대로 냈다면 {abs(total)}원 덜 받았어요({부분})" / 같음 "추천대로 냈어도 받는 혜택은 같았어요".
  - 이유 문장 (내 판단: 더 받은 경우에도 이유를 붙인다): 덜 받음은 지금 `reason_of`(구간 내려감 → 가장 많이 덜 받은 결제 → 가장 많이 줄어든 항목). 더 받음은 구간이 올라간 카드 → 가장 많이 더 받은 결제 → 가장 많이 늘어난 항목 순으로 하나. 같음은 이유 없음.
  - 카드 이름 뒤 조사가 영문 끝 글자에 따라 틀리지 않게 조사가 필요 없는 문장으로 쓴다.
- OpenAI 프롬프트의 예시는 실제 카드 이름·금액이 없는 자리표시로만 쓴다. `prompt_version` 2026-11-22.3.
- 확인: 데모 사용자 1~5와 덜 받은 사용자 23·28·44 를 실제 OpenAI 로 다시 돌린다.

검토에서 `.3` 프롬프트의 예시가 `base_reason` 과 어긋나는 문장을 부른다는 지적이 나왔다. 기본 카드를 구간 지키기로 정한 1·3·4·44번에게서

**사용자 결정:** 전략 문장도 엔진이 정해진 문장으로 쓰고, OpenAI 는 방식·기본 카드 이야기를 하지 않는다.

- 응답 `summary` = `{"headline": OpenAI, "effect": [엔진 0~2], "strategy": [엔진 1~2], "points": [OpenAI 1~2]}` (앱은 이 순서로 보인다).
- 엔진 전략 문장 (`report_copy.strategy_lines`): ① 방식과 고른 근거 — 월간 맞춤이면 비교표에서 이 방식이 혼자 가장 컸을 때만 '가장 컸던',
  같은 금액이 여럿이면 '그중', 더 큰 방식이 있었는데 차이가 작아 처음 방식을 뒀으면 '차이가 크지 않아'. 규칙·사용자 확정·이력 짧음·기본도 따로.
  ② 지금 기본 카드 — 엔진이 기본 카드를 정한 단계(`strategy.base_source`, `ranker.choose_base`)를 그대로 따른다:
  구간 지키기·월말 우선 채우기는 "다만 … 어느 방식이든 먼저 …, 지금은 {카드} 실적부터 채우고 있어요", 방식이 고른 카드는 "지금은 {카드} 실적부터 채우고 있어요",
  손해 방지·채울 곳 없음·실적 안 채움·모든 카드 채우기 끔은 "실적을 먼저 채우는 카드가 없어요", 고정 규칙은 "설정하신 규칙대로 지금은 {카드}부터 보여 드려요",
  프로모션 카드 화면(기본 카드를 다시 정하지 않음)은 기본 카드 문장 없음. 카드 이름 바로 뒤에는 조사를 붙이지 않는다.
- OpenAI 사실에서 `strategy` 를 통째로 빼고, 카드별 숫자(지난달·이번 달 혜택, 지난달 실적, 첫 구간 달성 여부와 모자란 금액, 이번 달 다음 구간까지 남은 금액)만 보낸다.
  검사기는 OpenAI 문장의 '추천'(모든 쓰임)·'방식'·'채우/채워/채웠'·'기본 카드'와 효과 표현('더 받/더받'·'덜 받/덜받'·'놓쳤/놓친'·'구간에 올라')을 거른다.
- 정해진 문구는 제목 + 효과 문장 + 전략 문장 + 카드 숫자 요점 틀. `prompt_version` 2026-11-22.4.
- 확인: 데모 1~5번과 덜 받은 23·28·44번을 실제 OpenAI 로 다시 돌린다.
- 카드별 숫자 검사 (사용자 결정, `2026-11-22.5`): `.4` 에서 23번 AI 가 실적 조건 없는 BC 케이퍼스트 카드에 다른 카드의 첫 구간 300,000원을 붙여 써서, 카드 이름이 나온 문장의 숫자는 그 카드의 값만 허용하고(두 장이면 둘 중 하나, 이름 없는 문장은 전체 사실), 이번 달 다음 구간은 '이번 달'을 붙이고, 요점 하나는 짧은 문장 1~2개·120자 이하, 금액은 천 단위 쉼표로 검사한다.

## 변경 (2026-11-22 심야): 요점 문장도 엔진이 쓰고 OpenAI 는 고르기만

전체 재검토에서 OpenAI 요점 문장 검사의 빈틈이 나왔다. 1번 사용자 사실로 일부러 틀린 문장 7개를 넣으니 모두 통과했다:

첫 구간에 못 미친 카드를 "넘겼어요", 달 바꿔치기("11월에 … 47,070원"), 사실에 없는 건수("250번").

| 방법 | 내용 | 장단점 |

| A. 엔진이 쓰고 OpenAI 는 고르기만 | 엔진이 카드별 후보 문장을 숫자까지 넣어 만들고, OpenAI 는 제목과 후보 번호 1~2개만 답한다 | 틀린 숫자·뒤바뀐 뜻이 나올 수 없다. 문장 말투는 늘 같다 |

**사용자 결정:** A. 후보에는 지난달 실제로 닿은 구간과 이번 달 그 구간을 지키기까지 남은 금액도 넣는다

- 후보 문장 (`report_copy.candidates_of`, 카드 순서대로 번호 1부터, 카드 이름 바로 뒤에는 조사를 붙이지 않는다):

  | kind | 문장 | 만드는 조건 |
  |---|---|---|
  | `prev_benefit` | {지난달}월에 {카드} 혜택은 ○원이었어요. | 지난달 혜택 > 0 |

  | `prev_short` | {카드} 첫 구간까지 ○원 모자랐어요. | 첫 구간 미달 |
  | `keep_tier` | 이번 달 {카드} ○만 원 구간을 지키기까지 ○원 남았어요. | 지킬 구간이 있고 남은 금액 > 0 |
  | `next_tier` | 이번 달 {카드} 다음 구간 ○원까지 ○원 남았어요. | 다음 구간이 있고, 지킬 구간과 다를 때 |
  | `this_benefit` | 이번 달 {카드} 혜택은 지금까지 ○원이에요. | 이번 달 혜택 > 0 |
  | `this_total` | 이번 달({이번 달}월)은 지금까지 카드 혜택 ○원을 받았어요. | 항상 (마지막 번호) |

  실적 조건이 없는 카드는 혜택 문장만 만든다. 후보마다 `amount`(그 문장의 금액)를 함께 보낸다.
- OpenAI 에 보내는 사실: `month`, `prev_month`, 혜택 합계 둘, `candidates`(`id`·`card`·`kind`·`amount`·`text`). 카드별 숫자 칸은 따로 보내지 않는다.
- OpenAI 답: `{"headline": "…", "picks": [번호 1~2개]}`. 응답 `summary.points` 는 고른 후보의 `text` 그대로 (응답 모양은 그대로),
  고른 번호는 `copy_log.picks`. 답에 다른 문장이 섞여 있어도 쓰지 않는다.
- 고르는 기준(프롬프트): 지난달 이야기 하나(혜택이 가장 컸던 카드, 또는 조금 모자랐던 카드)와 이번 달 이야기 하나
  (구간까지 남은 금액이 가장 작은 것, 구간 문장이 없을 때만 이번 달 혜택).
- 검사 (`check_copy`·`check_headline`): `picks` 는 있는 번호 서로 다른 1~2개. 제목의 숫자는 지난달 '○월'(그 해 '○년')과
  지난달 혜택 합계 '○원'만, 쉼표까지 값 그대로 (100배·반올림·줄임·다른 금액·건수는 걸린다). 금액을 쓰면 '○월'이나 '지난달'이 있어야 하고
  '이번 달'과 함께 쓰지 못한다. 카드 이름·효과·전략 표현·저장 주장·소비 권유 금지, 40자 이하. (제목 규칙의 세부는 구현하며 정했다.)
- 없앤 검사: 요점 문장용이던 카드별 숫자 검사, 120자·문장 수, 천 단위 쉼표, '이번 달 다음 구간' (요점을 OpenAI 가 쓰지 않으므로).

  |---|---|
  | 이번 달 결제는 있는데 혜택 0원 (요점) | 이번 달(11월)은 아직 받은 카드 혜택이 없어요. |
  | 이번 달 결제가 없음 (요점) | 이번 달(12월)은 아직 결제가 없어요. 결제하면 받은 혜택을 여기서 알려 드려요. |

  | 이번 달 전 결제가 하나도 없음 (제목) | 첫 리포트예요. 다음 달부터 지난달 혜택을 정리해 드려요. |

  지난달 혜택이 0원이면 제목은 엔진이 쓰고(`fixed_headline`, 응답 `has_history` 로 첫 리포트 구분) OpenAI 는 고르기만 한다.
  결제 이력이 없는 사용자의 전략 문장("채울 만한 곳이 없어…")은 이번에 바꾸지 않았다.
