# 백엔드 가상 POS 설계 (짧은 설계)

2026-11-25 · 상태: 팀 확인 (2026-11-25 "설계대로 진행")

## 왜
배포한 앱(Amplify 웹, 서버 `https://paymate.duckdns.org`)에서는 결제할 방법이 없다. 앱의 '시연 결제' 버튼은 최종본에서 뺐고,
가상 POS 는 맥에서만 켜는 `demo/` 파이썬 서버에 있다. 발표·시연 때 배포 환경에서도 **손님 앱 QR → 가상 POS 결제**를 보여 주려고 한다.

## 목표 / 하지 않을 것
- 목표: 백엔드가 가상 POS 화면을 직접 보여 준다. `https://paymate.duckdns.org/pos` 에서 가맹점·금액을 고르고 카메라로 앱 QR 을 찍으면 승인된다.
- 목표: 만능 키는 서버 안에만 둔다 (브라우저에 보내지 않는다). AI 가 느리거나 꺼져도 POS 는 돈다.
- 하지 않음: 실제 결제망·단말기 연동, POS 로그인, `demo/` 파이썬 서버 수정(로컬용으로 그대로 둔다), 앱 PWA(다음 작업으로 따로).
- 실패로 볼 것: 키가 화면 코드에 드러나는 것, POS 를 켜려고 백엔드 시작이 실패하는 것, 기존 `/api/v1/pos/payments` 동작이 바뀌는 것.

## 방법 (고른 것: A)
| 방법 | 내용 | 결정 |
|---|---|---|
| **A. 백엔드에 넣기** | Spring 이 POS 화면 + 시연용 API 3개 제공 | **팀 선택 (2026-11-25)** — https 라 카메라 됨, 키 숨김, 서버 추가 없음, 코드가 GitHub 에 남음 |
| B. 파이썬 서버 EC2 에 올리기 | `demo/` 를 컨테이너로 하나 더 | 설정이 서버 전용 파일에만 남고 Caddy 경로가 백엔드 `/api` 와 겹침 |
| C. 앱 안에 POS 화면 | 손님 앱에 섞기 | 결국 A 의 API 가 필요하고 화면도 새로 만들어 일이 가장 많음 |

## 설계
**켜고 끄기** — 새 환경 변수는 만들지 않는다. 기존 `POS_DEMO_TERMINAL_KEY`(16자 이상)가 있으면 시연용 POS 가 켜지고, 없으면
아래 API 3개가 404 를 돌려준다. 화면은 404 를 받으면 "시연용 POS 가 꺼져 있어요" 를 보여 준다. (내 판단: 키가 이미 '시연 모드' 스위치 역할이라 하나로 둔다.)

**API** (모두 로그인 없이, SecurityConfig permitAll)
- `GET /api/v1/pos/demo/merchants` — 단말기가 있는 가맹점 목록 `[{merchantId, merchantName, branchName, category, categoryName}]`, 업종 순·이름 순. DB(`merchants`·`terminals`·`categories`)에서 바로 읽는다 (AI 안 거침).
- `POST /api/v1/pos/demo/payments` — 본문 `{code, amount, merchantId}`. 서버가 만능 키 경로와 같은 계산(그 가맹점 단말기, `process`)으로 승인·거절하고 기존 `PosPaymentResponse` 를 돌려준다. 금액 100원 ~ 1,000만 원.
- `GET /api/v1/pos/demo/transactions?limit=20` — POS 거래 최근 20건(`pos_transactions` 기준): 시각, 승인/거절(사유), 승인번호, 가맹점, 업종, 금액, 카드 상품명, 혜택 합계. (내 판단: 시연 데이터라 모든 사용자 거래를 보여 준다. 사람 이름·카드 번호는 넣지 않는다.)

**화면** — `backend/src/main/resources/static/pos/` 에 `demo/static/pos.html`·`style.css` 를 옮겨 와 위 API 를 부르게 고친다. `/pos` 로 들어오면 이 화면으로 간다.
가맹점 고르기(업종별 묶음), 금액, 18자리 번호 직접 입력, 카메라로 QR·바코드 찍기(BarcodeDetector, 없으면 ZXing 을 jsDelivr 에서), 승인 결과(혜택·프로모션), 최근 거래 3초마다 갱신.
옛 시연 전용 부분(데모 사용자·시연 시각 고르기, 가장 유리했던 카드)은 뺀다 (내 판단: 백엔드에는 그 정보가 없고, 앱 결제 완료 화면이 이미 보여 준다).

**시험** — 백엔드 시험: 키 없으면 3개 API 404, 가맹점 목록 형태, 결제 승인·재사용 거절·형식 오류·없는 가맹점, 금액 범위, 거래 목록 순서·개수, 기존 `/api/v1/pos/payments` 그대로. 로컬 DB(solpay_v21)로 앱 QR → `/pos` 결제 → 앱 '결제 완료'·최근 내역까지 브라우저로 확인하고 시험 행은 지운다.

## 배포 (구현 뒤, 그때 다시 묻는다)
팀원 EC2(`~/golla-card`, 지금 final 90c4f31)에서 final 을 받아 오고, `.env` 에 `POS_DEMO_TERMINAL_KEY` 를 더한 뒤 백엔드 컨테이너를 다시 빌드한다.
백엔드만 새 코드로 올리면 옛 AI 와 맞지 않는 곳이 있을 수 있어, AI 도 같이 올릴지 그때 정한다. 서버에 쓰는 일은 팀 확인을 받고 한다.

## 만드는 사람에게 맡기는 것
클래스·메서드 이름, `/pos` 주소 연결 방법(리다이렉트 또는 뷰 컨트롤러), 시험 방식(기존 백엔드 시험 방식을 따른다), 화면 문구의 세부.
