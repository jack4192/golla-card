# 행사(카드사 이벤트·마이샵) 목록을 DB 로 옮기기 설계 (2026-11-23)

## 왜

앱 혜택 탭·홈 미리보기·오늘의 프로모션 팝업·알림은 앱 코드에 박힌 행사 목록(`frontend/data/promotions.js` 6건 +
`screens/MainScreen.js` 의 `MYSHOP_ROWS` 25건)과 로고 28장을 쓴다. 그런데 AI 챗봇·카드 배치·맞춤 추천은 DB `promotions` 표(29건)와
AI 쪽 `data/config/promotions.yml`(31건)을 합친 목록을 쓴다. 지금은 같은 엑셀에서 나와 내용이 같지만 세 군데를 따로 고쳐야 하고,
가게 이름 표기가 달라(예: 앱 '온라인 다이소몰' / DB '다이소몰') 맞춤 추천 가맹점 탭에서 로고가 빠진다.

## 팀 결정 (2026-11-23)

| 항목 | 결정 |
|---|---|
| 목적 | **챗봇·추천과 같은 목록을 보여 주기**, **앱 데이터를 최대한 없애기** |
| 방식 | **B: 전부 DB 로 옮기고 AI·백엔드가 같은 DB 표를 읽는다** (내 추천은 A 였음, 아래 '방식') |
| 식별불가 마이샵 2건 ('미식 브랜드(식별불가)', '종합쇼핑몰(식별불가)') | **아예 뺀다.** DB 에 넣지 않고, 앱 혜택 탭에서도 사라지고, `promotions.yml` 에서도 지운다 → 행사는 29건 |
| 데모 모드(서버 주소 없이 켠 앱) | **서버 전용.** 앱에 행사 사본을 남기지 않는다. 데모 모드에서는 행사가 보이지 않는다 |

데모 모드 결정의 영향: 팀원의 웹 배포 스크립트(`frontend/웹배포_실행.cmd`, AWS Amplify)는 서버 주소 없이 빌드하므로
그 웹 시연 페이지의 혜택 탭은 안내 문구만 보이게 된다.

## 목표 / 하지 않을 것 / 실패로 보는 것

- 목표
  - 행사 29건의 화면 정보(이름·혜택 문구·실제 기간·지급일·결제 방법·유의사항·확인 필요·로고)를 DB `promotions` 표에 둔다.
  - AI 는 yml 대신 이 표만 읽고, 백엔드는 같은 표로 혜택 탭용 API 를 준다.
  - 앱에서 행사 목록·로고 연결표·로고 파일을 지운다.
- 하지 않을 것
  - 행사 관리 화면(추가·수정 UI), 행사 데이터 내용 변경(문구·금액·기간은 지금 화면 그대로 옮긴다).
  - 1년치 가상 결제에 붙은 행사 기록(`payments.promotion_id`) 변경, 결제 데이터 재생성.
  - 다른 세션의 v2·v2.1 데이터 폴더 변경.
  - 웹 배포 스크립트를 서버 모드로 바꾸기.
- 실패로 보는 것
  - 혜택 탭과 챗봇 목록이 서로 다른 행사·기간을 말하는 것.
  - 혜택 탭이 '2025-11-01부터' 같은 가상 데이터용 기간을 보여 주는 것.
  - 카드 배치·재생 평가 결과가 바뀌는 것 (점수 계산은 지금과 같아야 한다).
  - 서버 모드에서 앱 데이터(행사 사본)가 다시 쓰이는 것.

## 방식

| 방식 | 판단 |
|---|---|
| A. AI 가 목록을 내려 주고 백엔드는 전달만 | 챗봇과 같은 코드라 어긋날 수 없고 RDS 변경이 없다. 지급일·유의사항은 yml 에 남는다 (내 추천) |
| **B. 전부 DB 로, AI·백엔드가 같은 표를 읽기 (채택)** | 행사 정보가 DB 한 곳에 있다. RDS 구조·데이터 변경, AI 행사 불러오기 수정, 기간 두 가지 관리가 필요하다 |
| C. 백엔드만 DB 를 읽기 | 가상 데이터용 기간이 보이고 지급일·유의사항이 없고 AI 목록과 어긋나 뺐다 |

## 1. DB: `promotions` 표에 화면용 칸 더하기

지금 칸(`start_date`·`end_date`·`value`·`min_amount`·`max_amount`·`kind` 등)은 그대로 둔다. 특히 `start_date`(대부분 2025-11-01)는
1년치 가상 결제와 맞물려 있어 바꾸지 않는다.

| 새 칸 | 형식 | 뜻 |
|---|---|---|
| `display_name` | varchar(100) | 화면 이름 ('온라인 다이소몰', 'W컨셉(앱/웹)', '차앤박(CNP)' 등). `merchant_name` 은 가맹점 찾기용 그대로 |
| `benefit_type` | varchar(10), point / cashback / discount | 혜택 종류 |
| `benefit_text` | varchar(60) | 화면 혜택 문구 (지금 앱 문구 그대로) |
| `display_start`, `display_end` | date | 실제 행사 기간 (화면·'지금 진행 중' 판단용) |
| `payout` | varchar(40) | 지급일 |
| `pay_method` | varchar(60) | 결제 방법 |
| `note` | varchar(200) | 유의사항 (없으면 NULL) |
| `needs_check` | boolean NOT NULL DEFAULT false | 응모·선착순·가맹점 식별 불가처럼 엔진이 확인할 수 없는 조건 |
| `logo_url` | varchar(200) | 로고 주소 ('/brand-logos/mega.png'), 없으면 NULL |

- 새 칸은 모두 NULL 허용(`needs_check` 만 기본값). 값이 없을 때 읽는 쪽은 `display_name` → `merchant_name`, `display_start/end` → `start_date/end_date` 로 대신한다.
- 행 수는 지금 DB 그대로 29건이다 (식별불가 2건은 팀 결정으로 넣지 않는다). 새 행을 넣지 않고 29건을 UPDATE 만 한다.

## 2. AI 엔진

- `db`·`teamdb` 저장소는 `promotions` 표 하나에서 행사를 읽는다. `promotions.yml` 을 읽지 않는다 (`loader.load_popup_promotions` 를 이 두 모드에서 쓰지 않음, `merge_promotions` 불필요).
- 점수 계산(카드 배치·결제 평가·재생): 지금처럼 `start_date`~`end_date` 기간, `needs_check` 행사는 뺀다 → 결과가 지금과 같아야 한다.
- '지금 진행 중' 판단(맞춤 추천 가맹점 탭·일정 팝업·챗봇 `list_promotions`)은 `display_start`~`display_end` 를 쓴다 (지금 yml 의 실제 기간을 쓰는 것과 같은 동작).
- 응답에 화면 정보를 싣는다: 맞춤 추천 행사(`offers`)와 챗봇 행사 목록에 `display_name`(화면 이름)·`logo_url`. 챗봇 목록의 기간은 실제 기간이 된다(지금은 DB 사본의 2025-11-01 이 보일 수 있음).
- **새 칸이 없는 데이터** (다른 세션이 실험 중인 v2·v2.1 폴더, 팀원이 가진 예전 zip, 마이그레이션 SQL 을 실행하기 전의 RDS·로컬 DB):
  그때만 `promotions.yml` 에서 같은 번호의 `needs_check`·실제 기간을 채운다 (내 판단, 검토 반영). 지금은 DB 행에 확인 필요 표시가 없고
  yml 이 5·6 을 막아 주므로, 칸이 없을 때 `needs_check=false` 로 보면 5·6 이 점수에 다시 들어가고(v1 에서 6번이 붙는 결제 512건)
  '진행 중'이 2025-11-01 부터로 넓어진다. 이렇게 하면 SQL 실행 순서와 상관없이 점수가 지금과 같다. 칸이 있으면 yml 은 읽지 않는다.
- parquet 저장소(데이터 생성기 `data/out`)는 이번 범위 밖 (지금처럼 yml).
- 검토에서 확인한 것: v1 팀 DB 기준으로 DB 행이 맞추는 가맹점은 모든 행사에서 yml 행이 맞추는 가맹점을 포함하고(SSG닷컴만 DB 3곳·yml 1곳),
  DB 기간이 yml 기간을 모두 덮는다 → 칸이 있는 데이터에서 yml 을 안 읽어도 점수는 바뀌지 않는다. 맞춤 추천·팝업의 SSG닷컴 행사는 가맹점이 2곳 늘 수 있다.
- 남는 어긋남(알고 받아들임): 점수는 `start_date`(2025-11-01~) 기간이라, 실제 시작 전 날짜에는 결제 화면 안내가 그 행사를 셀 수 있다
  (예: 11-10 에 다이소데이(실제 11-16 시작)). 실제 시작일이 11-01 이 아닌 행사는 3·5·7번뿐이고 마지막이 11-20 이라, 오늘(11-23) 이후로는 나타나지 않는다.
  점수까지 실제 기간으로 바꾸면 월간 리포트의 지난달 비교·재생 평가 숫자가 바뀌어 하지 않는다.

## 3. 백엔드

- `GET /api/promotions` (로그인 필요): DB `promotions` 29건을 혜택 탭 형식으로 돌려준다. 정렬 = 이벤트 먼저, 그다음 번호 순.
  ```json
  [{"promotionId": 1, "kind": "event", "name": "메가MGC커피", "benefitType": "point", "benefitText": "500 마이신한포인트 적립",
    "minAmount": null, "maxAmount": null, "start": "2026-11-01", "end": "2026-11-30", "payout": "2026-12-13",
    "method": "신한 슈퍼SOL/SOL페이 바코드 결제", "note": "키오스크에서 바코드 스캔 필요", "needsCheck": false,
    "logoUrl": "/brand-logos/mega.png"}]
  ```
  `minAmount` 는 0 이면 null, `start/end` 는 실제 기간(없으면 `start_date/end_date`). 기간 필터는 하지 않는다 (앱이 '기간 내/예정/종료'를 표시).
- 로고 28장을 `backend/src/main/resources/static/brand-logos/` 에 둔다 (앱 `assets/promotion-logos`·`myshop-logos` 의 같은 파일). 카드 이미지(`/card-images/**`)처럼 로그인 없이 받게 보안 설정에 더한다.
- 백엔드 엔티티는 만들지 않는다 (네이티브 조회, 기존 `CardRepository` 방식). 그래서 RDS 에 새 칸을 넣기 전에도 백엔드는 켜진다 (`ddl-auto: validate` 대상이 아님). 단 칸이 없으면 이 API 는 오류.

## 4. 앱 (서버 모드에서만 행사가 보인다)

- 새 파일: 행사 API 를 읽고 앱 화면 형식으로 바꾸는 순수 함수 파일 + 한 번 읽으면 앱을 다시 열 때까지 기억하는 읽기 함수 (카드 상품 목록 `serverCatalog.js` 방식).
- 바꾸는 곳: 혜택 탭 목록·검색·필터, `BenefitReport`·'이번 달 혜택 N건', 홈 미리보기, 오늘의 프로모션 팝업(`RecommendationLaunchPopup`), 아침 알림(`refreshDailyNotifications` 의 행사),
  앱 기본 안내 챗봇 답(`localAnswer`), 맞춤 추천 가맹점 탭 로고(`PromotionOffer`: AI 가 준 `logo_url`), 로고는 서버 주소를 붙여 그림.
- 데모 모드: 혜택 탭에 '서버에 연결하면 진행 중인 행사를 볼 수 있어요', 홈 미리보기·오늘의 프로모션 팝업·행사 알림 없음, 데모용 행사 추천(`RoutineRecommendationScreen` 의 `recommendPromotion`)도 없음.
- 지우는 것: `data/promotions.js`, `data/promotionBrands.js`, `data/myshopLogos.js`, `MainScreen.js` 의 `MYSHOP_ROWS`, `assets/promotion-logos/`, `assets/myshop-logos/`.
  `selectDailyPromotion` 같은 고르기 함수(코드)는 새 파일로 옮긴다.
- 서버에서 못 읽으면: 혜택 탭에 '행사를 불러오지 못했어요 · 다시 시도', 다른 곳은 행사 없이.

## 확인 방법

- AI: 새 칸을 읽는 저장소 테스트(칸 있음·없음), 점수 계산 결과가 바뀌지 않는지(재생 평가 혜택률이 지금과 같음), 챗봇 목록·맞춤 추천 행사가 실제 기간·화면 이름·로고를 싣는지, 확인 필요 5·6 이 점수·챗봇 목록에서 빠지는지.
- 백엔드: `/api/promotions` 29건·정렬·대신 규칙 테스트, `/brand-logos/mega.png` 로그인 없이 200.
- 앱: 순수 함수 테스트(API → 화면 형식, 기간 상태), 웹 빌드, 서버 모드 브라우저 확인(혜택 탭 29건·로고, 식별불가 2건 없음, 홈 미리보기, 맞춤 추천 가맹점 탭 로고), 데모 모드 안내 문구.
- DB: RDS·로컬에 SQL 실행 뒤 29건·새 칸 확인 (RDS 는 읽기 전용 계정으로 확인).

## 구현 위치

- AI·데이터 생성기: `ai/placement-engine` 에서 딴 별도 작업 폴더·브랜치 (원래 폴더에는 다른 세션의 커밋 전 데이터 생성기 변경이 있다). 끝나면 `ai/placement-engine` 에 합치고 `final` 에 합친다.
- 백엔드·앱: `final` 에서 딴 별도 작업 폴더·브랜치. 사용자가 띄운 8031·8090·8081 은 건드리지 않는다.
- RDS 마이그레이션은 사용자가 실행. 커밋·푸시·`final` 합치기는 팀 피드백 때.

## 구현하며 정한 것

1. 새 칸을 `promotions` 표에 직접 더한다 (따로 표를 만들지 않음). 기존 칸·기간은 그대로.
2. 화면 문구(이름·혜택 문구·지급일·결제 방법·유의사항)는 지금 앱 화면 값 그대로 옮긴다. 혜택 문구는 숫자에서 만들지 않고 칸에 저장한다.
3. 점수 계산은 지금 기간(`start_date`~)을, '지금 진행 중' 판단과 화면은 실제 기간을 쓴다.
   (실제 시작 전 며칠 동안 결제 화면이 행사를 셀 수 있으나 11-20 이후로는 생기지 않는다.)
7. 새 칸이 없는 데이터에서는 yml 로 확인 필요·실제 기간을 채워, SQL 실행 전이나 v2·v2.1 데이터에서도 점수가 지금과 같게 한다.
4. 백엔드는 엔티티 없이 조회만 해서, RDS 변경 전에도 백엔드가 켜지게 한다.
5. 로고는 백엔드가 직접 제공하고 DB 에는 주소만.
6. 챗봇 행사 목록이 실제 기간·화면 이름을 말하게 된다 (지금은 '2025-11-01' 이 보일 수 있음).
